# Практика 3.1 — Django ORM

Практику делаем на моделях **ЛР2** (`CarOwner`, `Car`, `DriverLicense`, `Ownership`), чтобы не загрязнять согласованную БД рекламного агентства дополнительными автомобильными таблицами.

Скрипт создаёт шесть автовладельцев, шесть автомобилей, шесть водительских удостоверений и двенадцать непересекающихся периодов владения. Каждый владелец связан с двумя автомобилями. После этого выполняются пять фильтрующих и пять агрегирующих запросов из задания преподавателя.

Запускать из папки `laboratory_work_2`, активировав **окружение ЛР2** и PostgreSQL из ЛР2:

```powershell
python ..\laboratory_work_3\practice_3_1\run_in_lab2.py
```

ЛР2 должна находиться по соседству с ЛР3 в той же ветке/рабочей копии. В вашем форке на момент подготовки архивa ЛР2 была в отдельной ветке `lab2`, а не в `main`. Если ЛР2 пока не объединена с веткой, куда добавлена ЛР3, запускайте практику в ветке со всеми лабораторными или после слияния ЛР2: **не копируйте модели автомобилей в проект агентства**.

В скрипте есть `get_or_create`: повторный запуск не плодит одинаковые демонстрационные данные. `select_related`/`prefetch_related` изучаются также в основном API ЛР3.

### Независимый запуск, если ЛР2 ещё не объединена с веткой `main`

Чтобы не зависеть от ветки ЛР2, приложена **учебная копия автомобильных моделей** в отдельной SQLite-базе. Основная PostgreSQL-база агентства не изменяется. Из корня ЛР3:

```powershell
python practice_3_1/manage.py makemigrations cars_practice
python practice_3_1/manage.py migrate
$env:PRACTICE_3_1_STANDALONE = '1'
python practice_3_1/run_in_lab2.py
Remove-Item Env:PRACTICE_3_1_STANDALONE
```

Для защиты покажите преподавателю оба варианта: оригинальный скрипт на моделях ЛР2 и автономный запуск. Не переносите эти четыре вспомогательные таблицы в агентство.
