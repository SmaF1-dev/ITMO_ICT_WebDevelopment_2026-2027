# Практическое занятие 3.1 — Django ORM

Практика выполняет задания на данных об автомобилях и владельцах из ЛР2. Исходный сценарий —
`run_in_lab2.py`: он создаёт шесть владельцев, шесть машин, шесть удостоверений,
двенадцать непересекающихся периодов владения, затем выполняет пять запросов фильтрации
и пять запросов с агрегированием/сортировкой.

## Автономная проверка

Выполнять из папки `laboratory_work_3`, активировав её виртуальное окружение:

```powershell
python practice_3_1/manage.py migrate
python practice_3_1/manage.py check
python practice_3_1/manage.py test cars_practice -v 2
$env:PRACTICE_3_1_STANDALONE = '1'
try {
    python practice_3_1/run_in_lab2.py
}
finally {
    Remove-Item Env:PRACTICE_3_1_STANDALONE -ErrorAction SilentlyContinue
}
python practice_3_1/manage.py runserver 127.0.0.1:8003
```

При открытии `http://127.0.0.1:8003/` показывается JSON со статусом и количеством
владельцев, машин, удостоверений и периодов владения. Это только страница состояния:
сама практика 3.1 посвящена Django ORM и запускается скриптом, **Swagger в ней нет**.
Порт 8003 используется отдельно, чтобы не конфликтовать с основным API ЛР3 на 8000
и API практики 3.2 на 8001. SQLite-база практики изолирована от PostgreSQL ЛР3.

## Запуск на исходных моделях ЛР2

В ветке с ЛР2 перейти в `laboratory_work_2`, активировать её окружение и запустить:

```powershell
python ..\laboratory_work_3\practice_3_1\run_in_lab2.py
```

Скрипт использует `project_first_app.models`, если переменная
`PRACTICE_3_1_STANDALONE` не задана. Он использует `get_or_create`, поэтому повторный
запуск не создаёт дубликаты демонстрационных данных. Дополнительные четыре таблицы
этой практики не добавляются в согласованную базу рекламного агентства.
